<h1>Delhivery Last-Mile Delay Intelligence Pipeline</h1>

This repository contains the complete end-to-end machine learning pipeline for Delhivery's regional operations. It predicts parcel delivery durations, flags at-risk shipments prior to promised service windows, audits operational hub tiers via clustering, and generates actionable daily playbooks for dispatch teams. This capstone project is a part of the Artificial Intelligence and Machine Learning Certification Program by E&ICT Academy, IIT Roorkee. The project uses the open-source Python libraries like  pandas, NumPy, scikit-learn, joblib.
  
<h2>How to run</h2>

The scripts should be run in the specified order because each script depends directly on data artefacts and CSV tables created by the previous one.
Clone the repository and set up the Python environment:

 pip install -r requirements.txt
 
<h2>Run the pipeline from root in this exact order:</h2>

1.Generate the data files (creates hubs.csv, raw_shipments.csv, new_shipments.csv)

python generate_data.py

2.Clean data, engineer features, and save data/modelling_table.csv

python part_a_clean_eda.py

3.Train and test regression models for delivery hours

python part_b_regression.py

4.Train classifiers, test feature selection, and pick the alert threshold

python part_c_classification.py

5.Segment the 24 hubs using K-Means and find tier mismatches

python part_d_segments.py

6.Save the final model pipeline and helper files to models/

python package_model.py

7.Clean and score new_shipments.csv and assign operational actions

python predict_delay.py

The models/delay_model.pkl file can be regenerated by running:

python package_model.py

The committed pickle file is compatible with the scikit-learn version pinned in requirements.txt. If a different version is installed, it is recommended to run package_model.py again instead of using the existing pickle file.

All random processes use random_state=42, except for the data generator, which uses its own fixed seeds. This ensures that repeated runs produce the same results. Also, running predict_delay.py multiple times produces identical output files.

<h2>Data findings</h2>

All observations below are calculated from outputs/part_a_checks.csv, outputs/part_a_delay_by_group.csv, and outputs/part_a_correlations.csv:

<h2>Service Type Delay Profile:</h2>

Express parcels experience the highest failure rate across the network at 0.4897 (119 delayed out of 243 shipments), followed by Standard at 0.2056 (132 delayed out of 642 shipments) and Economy at 0.0857 (27 delayed out of 315 shipments). Express deliveries have the shortest promised delivery time of 36 hours, leaving very little buffer to handle problems.

<h2>Delays by hub tier:</h2>

As we go from Tier 1 to Tier 3, delays go up very fast. Tier 1 hubs have a delay rate of 0.04 (16 of 400), Tier 2 hubs have a delay rate of 0.215(86 of 400), and Tier 3 hubs reach 0.44 (176 of 400).

<h2>Delays by distance:</h2>

Longer routes have much higher delay rates. For 0-200 km, the delay rate is only 0.0219 (6 of 274). It increases to 0.1368 (77 of 563) for 201-400 km, jumps to 0.4364 (120 of 275) for 401-600 km, and reaches 0.8523 (75 of 88) for trips over 601+ km.

<h2>Strongest correlations with delivery hours:</h2>

Looking at part_a_correlations.csv, the three features most correlated with delivery_hours are:
promised_hours: 0.8371
distance_km: 0.4013
hub_tier: 0.3175

<h2>Why declared value is log-transformed:</h2>

In the median-filled data, declared_value has a mean is INR1533.05 and a median is INR 1121.50, which shows it is skewed by a few expensive parcels. After taking the natural log, log_declared_value has a mean of 7.0277 and a median of 7.0224, which makes the distribution much more balanced and easier for the models to learn from.

<h2>Data cleaning in numbers (from part_a_checks.csv):</h2>

24 missing parcel weights  and 12 messy service-type spellings collapsed to 3. After the hub merge there are still 1,200 rows and 0 missing cells across the 17 features delivery_hours and is_delayed.

<h2>Model results (regression)</h2>

We split the 1,200 rows into train (840), validation (180), and test (180). Models were evaluated using the 17 features to predict delivery_hours:

Baseline model: Predicting the mean of y_train for all validation parcels gives a validation R^2 of -0.0212(RMSE of 18.85 hours). A negative R^2 means that simply using the average value is worse than a simple horizontal line.

<h2>Best validation model:</h2>

Linear regression, with validation RMSE 4.8912 hours (R² 0.9313). Gradient boosting was almost identical (RMSE 4.9165, R² 0.9306), then random forest (5.5095, R² 0.9128) and the decision tree (6.2796, R² 0.8867).

Tree depth experiment: Looking at part_b_tree_depth.csv:
0.1 is best (validation R² 0.9306). With 0.01 (R² 0.7127) each of the 100 trees corrects only 1% of the error, so the ensemble is too slow and underfits. With 1.0 (R² 0.8439) each tree's correction is applied in full, so the ensemble overshoots and chases noise.

The best depth on validation is depth 6, with a validation RMSE of 6.28 hours (train RMSE of 4.71 hours).
With unlimited depth, the tree completely overfits (high variance): train RMSE drops to 0.00 hours while validation RMSE goes up to 7.84hours (a big gap of 7.84hours).

Cross-validation and final choice: Running 5-fold cross-validation on the 1,020 train+val rows, Gradient Boosting had a mean R^2 of 0.9353 (std 0.0045) compared to Linear Regression's 0.9261(std 0.0047). Because Gradient Boosting had both the best validation RMSE and the better CV score, picked it as the final model. On the test set, it scored an R^2 of 0.9492 (RMSE 4.52 hours).

<h2>Model results (classification)</h2>

For predicting is_delayed, i used a stratified split (195 delayed in train, 42 in validation, 41 in test):
Blind baseline: Predicting "not delayed" for every single parcel gives an accuracy of 0.7667 (76.67%). But it gets TP=0 and recall=0.0, which means it catches zero delayed parcels. This shows why accuracy alone is misleading for an imbalanced problem.

Noise columns and feature signals: The five noise columns carry 0.223 of the default forest's total importance, even though they carry no signal.The forest spreads splits over them. By F-score all five fall outside the top 7 (ranks 8,17,12,14,16) and each has an F-score below 10 (highest 4.5847), while the lowest F-score among the top seven is 36.7281 (part_c_feature_scores.csv). The top seven are distance_km, hub_tier, hub_daily_capacity, n_stops, promised_hours, rain_flag and sale_event_flag.

Feature selection (k sweep): In outputs/part_c_selectk.csv, keeping only the top k=7 features gave the best validation F1 of 0.8333. Using all 17 features dropped validation F1 to 0.7848 because the tree branches get wasted on meaningless noise columns.

Tuning results: In outputs/part_c_tuning.csv, Grid Search (27 candidates, 135 fits, best CV accuracy 0.8952) got a validation F1 of 0.775. Randomized Search (9 candidates, 45 fits, best CV accuracy 0.8905) got a validation F1 of 0.7848. The default untuned Random Forest on the same 7 features beat both, keeping a validation F1 of 0.8333. This happens because tuning restricted tree depth and leaf sizes on a small 180-row validation set, whereas the default forest ensemble worked better on borderline rows.

Choosing the threshold: In operations, missing a late parcel is much worse than making an extra phone call. The operations rule says we must pick the highest threshold with validation recall of at least 0.80:

Threshold 0.6 gives recall 0.7619 (too low); threshold 0.5 gives recall     0.8333 with precision 0.7955 (TP 35, FP 9, FN 7); lowering to 0.4 raises recall to 0.8809 but precision falls to 0.74, and at 0.1 precision is only 0.4824. The highest threshold meeting the rule is 0.5.

Test result (part_c_final_test.csv, scored once). At threshold 0.5: TN 125, FP 14, FN 10, TP 31; accuracy 0.8667, precision 0.6889, recall 0.7561, F1 0.7209. Test recall (0.7561) is lower than validation recall (0.8333) and below the 0.80 target. With only 41 delayed parcels in the test set, 31 caught instead of the 34 that would give 0.83 is a small absolute difference, so it is partly sampling noise, but I do not claim the 0.80 recall target is met on unseen data.

<h2>Operations recommendation</h2>

Escalate segment. K-Means on the hub profiles (hub_segments.csv, segment_profile.csv) puts nine hubs in Escalate, with a segment delay rate of 0.4600, mean delivery 64.6504 hours, mean distance 470.4757 km and 84.3444 stops: Nagpur (0.46), Kochi (0.36), Patna (0.46), Ranchi (0.38), Guwahati (0.62), Raipur (0.48), Bhubaneswar (0.40), Siliguri (0.44) and Agartala (0.54). Watch has 8 hubs (delay rate 0.1550) and Standard 7 hubs (0.0257).
Tier labels that mislead (tier_vs_segment_mismatch.csv):

Kolkata (Tier 1) behaves like a Watch hub, so the Tier 1 label overstates its reliability.
Nagpur (Tier 2) and Kochi (Tier 2) behave like Escalate hubs, so the Tier 2 label understates their risk.
Dehradun (Tier 3) behaves like a Watch hub, so the Tier 3 label is too pessimistic. Operations should assign playbooks from the data-driven segment and treat the tier label as a static attribute only.

Alert threshold. Flag a parcel when its delay probability is at least 0.5. On the test rows, about 7 of every 10 flagged parcels are really delayed (precision 0.6889) and about 8 of every 10 delayed parcels are caught (recall 0.7561, that is 7.6 of 10); the validation recall was 0.8333, so plan for roughly 75 to 83 percent.

New parcels. Of the 48 new parcels in new_shipment_actions.csv, 8 are flagged; 6 of those sit in Escalate hubs and need a hub-manager escalation, and the other 2 get a proactive customer call. The remaining 40 need no action.

Why K = 3. The across-to-within ratio (part_d_separation.csv) is 2.894 for K=2, 5.3928 for K=3, 6.3047 for K=4 and 6.8866 for K=5. The largest jump comes from 2 to 3 (+2.4988); after that it adds only +0.9119 and +0.5819. K=4 has cluster sizes 8-7-5-4 and K=5 has 8-7-4-3-2, so each contains a cluster of fewer than 6 hubs, too small to carry its own playbook, and the business runs exactly three playbooks. K=3 gives sizes 9-8-7 with clearly separated delay rates.

<h2>Production plan</h2>

(a) Production-readiness characteristics mapped to repository items

Accuracy: held-out validation and test metrics in part_b_metrics.csv and part_c_final_test.csv, with the blind baseline for comparison.

Reliability: clean_shipments handles duplicates, casing, missing values, the 999 kg sentinel and the unknown payment mode; predict_delay.py asserts no missing feature values.

Reproducibility: pinned requirements.txt, committed generate_data.py, fixed random_state=42, and the run order in "How to run".

Performance (speed): the model scores a whole batch in one predict_proba call and the RandomForest with seven selected inputs is small enough to run inside the scoring script on demand.

Maintainability: one shared module src/shipment_prep.py, one script per Part, and constants (FEATURES, PROMISED_HOURS) defined once.

Consistency: training and prediction use the same clean_shipments and build_features, with the stored medians in models/impute_values.csv and the column order in models/feature_order.csv.

Monitorability: new_shipment_actions.csv stores the delay probability, flag, segment and action for every parcel, so each can be compared with the real outcome later.

(b) Quantities to monitor, with triggers Weekly delayed share of delivered parcels. The training share is 0.2317; investigate if a week is outside 0.17 to 0.29 for two weeks running.

Weekly share of parcels flagged. On the test rows 45 of 180 parcels (0.25) were flagged; investigate if the weekly flagged share leaves 0.15 to 0.35.

Recall on parcels whose outcome is now known, over a rolling four weeks with at least 40 delayed parcels. Test recall was 0.7561; retrain if it falls below 0.65.

Share of missing distance_km or parcel_weight_kg values in the incoming data. In the training export about 3 percent of distances (36 of 1,200) were missing,alert if a week exceeds 10 percent, since the median fill would then dominate.

<h2>Limitations</h2>

The data is synthetic: effects such as the sale-window delay and the four hubs that operate unlike their tier label were built into the generator, so real shipments will be messier and the scores here are likely optimistic.

The test set has only 41 delayed parcels, so test recall (0.7561) and precision (0.6889) carry wide uncertainty; a change of a few parcels moves them by several points.

The 0.5 threshold and the final configuration were chosen on one 180-row validation split (42 delayed parcels), and the three candidate configurations were within noise of each other, so another split could choose differently.

The regression winner (linear regression) and the model I recommend shipping (gradient boosting) differ; only the former was scored on the test rows.

The hub profiles and K-Means segments are computed from all 1,200 parcels (50 per hub, 24 hubs), so the segments are only as stable as these small samples, and K-Means results for K=4 and K=5 depend on the seed and hub order.

The packaged classifier is fitted on the 840 training rows only (not training plus validation), and the pickle depends on the exact scikit-learn version.
